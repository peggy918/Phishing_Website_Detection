## 1. 先講清楚這份比較是什麼

- 這是 **AI 操作瀏覽器的模擬測試，不是真人使用者測試**，不能當作 G1 訪談或使用者驗證的證據。
- MCP 測試由 AI 決定操作步驟並判斷結果，每次操作可能不同；pytest 是固定腳本。
- 測試網址是本機（`127.0.0.1`）加暫存資料庫，**沒有經過真實網路或 Cloudflare Tunnel，也沒有連 SQL Server**。
- 程式全程維持定版狀態（`23008fa`，標籤 `v1.0-review`），測試期間沒有修改。測完後本人決定在初審前修正 F1，其餘問題只記錄、未修正。

## 6. 發現的問題

F1 已在測試後修正，其餘未修正。嚴重程度是 AI 的判斷，請本人核對。

### 中

**F1 貼入去連結格式時，顯示英文技術訊息**
- 重現：在首頁輸入 `hxxp://tw06[.]shopeelem[.]xyz/` 後按檢查。
- 結果：400，顯示「無法解析：Invalid IPv6 URL」，`hxxps://shopee[.]tw/` 也一樣。
- 影響：這正是本網站自己顯示的格式，使用者複製回來重查的機率不低；訊息看不懂，也把程式內部的例外文字顯示出來（`app/services/normalizer.py:164`）。不會造成誤判，只是查不了。
- **已修正（2026-11-07，本人決定在初審前修）**：正規化先還原去連結格式（開頭的 `hxxp`／`hxxps`、全文的 `[.]` 與 `[:]`），解析失敗時改顯示中文訊息。補了單元、整合、E2E 測試，包括「去連結後再輸入，正規化結果與判定都不變」。
- 不影響模型：用修改後的程式重算訓練資料 16,629 筆的 48 個特徵，與原本的值逐格比較，0 格不同；另檢查 5 個資料檔共 41,549 個網址或網域欄位，還原函式都沒有改動任何字元（唯一含 `hxxp` 的 Kaggle 網址，`hxxp` 不在開頭，不受影響）。因此不需重新訓練。
- 本文件其餘結果都是在修正前的 `23008fa` 上測得。

**F2 中文網域沒有被判為冒用品牌**
- 重現：輸入 `https://蝦皮.tw/`（只當文字輸入，沒有連線）。
- 結果：顯示「未發現明顯風險跡象」，沒有任何判斷原因，p=0.2641，畫面上只有 `hxxps://xn--oyyp07a[.]tw/`。
- 原因：離線驗證 `brand_match.match()` 回傳無品牌。比對用的是編碼後的 `xn--` 字串，不會還原成中文，所以 `brands.yaml` 裡的別名「蝦皮」比對不到。
- 影響：這是漏判類的問題，使用者也認不出編碼後的網址。這只是一個例子，**不代表整體的漏判率**。

**F3 潛在問題：HTTPS 下所有表單可能被 CSRF 擋下（目前應不會觸發）**
- 觀察：DevTools 顯示，因為 `Referrer-Policy: no-referrer`，瀏覽器送出表單時沒有 `Referer`（`origin` 為 `null`）。
- 驗證：用 Flask 測試客戶端和暫存資料庫實測。Flask 認定是 HTTPS 又沒有 `Referer` 時，回 400「請求無效」；有 `Referer`，或走 HTTP，就會通過 CSRF。
- 影響：目前程式沒有 `ProxyFix`，也沒有 `WTF_CSRF_SSL_STRICT` 設定，所以經 Tunnel 時 Flask 應該仍視為 HTTP，不會觸發。**這是依程式推論，沒有實際跑 Tunnel。** 如果複審時加了 `ProxyFix` 或直接跑 HTTPS，所有表單都可能失敗。建議複審外部測試前先實測。另外 `SESSION_COOKIE_SECURE` 未設定，複審時可一併考慮。

### 低

**F4 CSRF 錯誤頁沒有追蹤碼**
- 重現：用瀏覽器工具刪掉表單裡的 `csrf_token` 後送出。
- 結果：400「請求無效」，頁面沒有追蹤碼；紀錄檔該筆 `request_id` 為 `null`。其他錯誤頁（例如 429）都有。
- 原因（依程式順序推論）：`csrf.init_app` 比 `begin_request` 先註冊，CSRF 檢查擋下時追蹤碼還沒產生（`app/__init__.py`）。
- 影響：真實使用者把頁面放太久、權杖過期時也可能遇到，這時無法用追蹤碼查紀錄。

**F5 沒有 favicon，每個新工作階段有一筆主控台錯誤**
- 重現：用新的瀏覽器工作階段開首頁，看主控台。
- 結果：`GET /favicon.ico` 回 404。不影響功能。

**F6 不同批次的重複紀錄會讓黑名單筆數變多**
- 重現：在已匯入真實 XML 的資料庫，再匯入 `tests/fixtures/gov_sample.xml`。
- 結果：顯示「匯入 15 筆（略過 0 筆）」，黑名單由 1,734 變 1,749，但不重複的通報編號仍是 1,734。
- 原因：唯一性是「批次＋編號」，只擋同一批次內的重複（`app/models/`、`app/services/gov_import.py`）。
- 影響：比對結果不受影響，但管理頁的「黑名單筆數」會偏高。如果政府每次提供的是累積檔，每次匯入都會再疊加；累積檔這點未查證。

**F7 靜態檔也是 `no-store`**
- 重現：連續換頁並看網路請求或 `/static/app.js` 的回應標頭。
- 結果：每次換頁都重新下載 `style.css`、`app.js`，因為 `no-store` 套用在所有回應上。本機效能不受影響；經 Tunnel 的影響未量測。

**F8 特殊 IP 寫法處理不一致**
- `http://[::1]/`：低風險，p=0.0518，沒有判斷原因；同時 `http://127.0.0.1:8080/admin` 是高風險、`http://[2001:db8::1]/login` 也是高風險。
- `http://2130706433/`（十進位 IP 寫法）：被判為「不是有效的網址」。

## 7. 限制與適合的用途

| | pytest E2E | Playwright MCP | Chrome DevTools MCP |
|---|---|---|---|
| 強項（本次實際用到） | 固定、可重複、已接上 GitHub Actions；能直接查資料庫斷言筆數 | 可用選擇器操作；可攔截請求（包括回應途中斷線）；主控台直接回報 favicon 錯誤 | 效能追蹤、Lighthouse、標頭檢視、網路降速與行動裝置模擬 |
| 限制（本次實際遇到） | 只驗證寫好的斷言；假模型結果不代表真實模型（情境 2）；速率限制關閉 | 沒有專用斷線工具，要靠 `run_code_unsafe`，它能執行任意程式，使用要小心；相對路徑的截圖會存到專案根目錄（已移走）；上傳要先觸發檔案選擇視窗 | **沒有請求攔截工具**，「回應途中斷線」未測；每次換頁都要重新取快照；網路清單只留最近 3 次換頁；沒顯示 favicon 錯誤 |
| 適合的用途 | 每次改程式後的回歸測試 | 探索腳本沒想到的操作，或快速重現問題 | 查效能、標頭、CSP 等診斷問題 |
| 不適合的用途 | 發現沒有事先想到的問題 | 當正式回歸測試（結果依賴 AI 判斷，每次操作可能不同） | 同左 |

## 8. 結論

1. **三種工具在 10 個情境裡，都沒有測出功能失敗。** pytest 有 3 個情境只算部分涵蓋（情境 5、9、10）。
2. **最重要的差異是模型，不是工具。** 情境 2 用假模型是中風險，用真實模型是高風險。這說明現有 E2E 驗證的是畫面流程，不是真實模型的判定，報告要分開說明。
3. **發現新問題主要靠「多試不同輸入」和「看到不同資訊」。** 8 個問題都不是 pytest 跑得出來的，但其中多數只要補測試就抓得到。
4. **三者適合互補，不是互相取代。** 依本次結果：pytest 留作回歸測試；Playwright MCP 適合探索操作；DevTools MCP 適合診斷。兩個 MCP 的呼叫次數差距，多半來自操作方式（選擇器、合併步驟），不足以說哪個整體比較好。
5. **這次比較規模小。** 每個工具只有一輪加少量重複，由同一個 AI 操作，不足以推論一般情況。

## 9. 沒有測到的部分

- **真實模型下的中風險頁面**：10 個情境都沒有在瀏覽器裡走到。離線算機率時，`https://esun-bank.com.tw/`（0.4446）和 `https://shopee.com.tw/`（0.7476）落在中風險區間，但只算了機率，沒有走過網站流程。「品牌規則把低風險拉高到中風險」在真實模型下也沒有走過。
- SQL Server、Cloudflare Tunnel、真實網路（F3 只用 Flask 測試客戶端模擬 HTTPS）。
- 真人使用者、真實手機（只有視窗縮小與行動裝置模擬）、Firefox、Safari、螢幕閱讀器。
- DevTools 的請求攔截（工具沒有）；多人同時操作（`testing-evidence.md` 另有量測）；權杖真正過期的情況。
- pytest 有、但這次 MCP 沒有測的：空白輸入、追蹤參數不改變顯示、404 頁的追蹤碼、按鈕「檢查中…」文字。
- 降速下的效能、首頁的 Lighthouse、Token 用量（皆未量測）。
