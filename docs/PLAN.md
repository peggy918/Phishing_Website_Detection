# PhishGuard 開發規劃（2026-10-31 版）

## 1. 系統目標

使用者輸入網址（複審時加入簡訊／LINE 截圖），系統判斷網址是否可疑，並說明原因。

偵測流程分三層：
1. 政府通報黑名單：已通報即判為高風險。
2. 白名單與品牌官方網域。
3. ML 模型：偵測尚未被通報的新變體。

## 3. 資料

### 3.1 資料來源

| 資料 | 用途 | 重點 |
|---|---|---|
| 數位產業署「通報 TWNIC 詐騙網址彙整表」XML（1,734 筆，全部是詐騙） | 黑名單＋訓練正例 | 見 3.2 |
| Kaggle：Web Page Phishing Detection Dataset（shashwatwork） | 訓練正負例 | 只用 `url` 欄位，自行重算特徵；下載後核對筆數與標籤分布 |
| 台灣正常網域（品牌官方網域＋Tranco 等熱門 .tw 網站） | 訓練負例＋誤判率測試 | 避免模型學成「台灣網址＝詐騙」 |
| 仿冒變體（參考 dnstwist 的變形規則自行產生） | 額外測試集 | 只產生字串，不查 DNS |

### 3.2 政府資料已知問題（清理時處理，也是報告素材）

- 同一網址拆成兩筆：含 www 與不含，或子網域與註冊網域（例如 318/319、327/330）→ 訓練前依註冊網域去重。
- 網址欄與網域欄不一致：46 號（laobeibi / aobeibi）、1207 號（jkpay-officiald.com / ezywalletc.net）。
- 網址缺少 scheme：172、401、1136 號之後；含 @ 的網址：1280、1281。
- 編號不是依時間排序（1320–1373 號的通報日期回到 2025-03/04）→ 時間切分必須依「接獲通報日期」。
- 平台型網域（github.io、carrd.co、netlify.app、weebly.com、cloudfront.net、vercel.app、pse.is、ubpages.com、myfreesites.net）：
  創建日期是平台本身的日期，且黑名單不可用註冊網域比對。
- 疑似一般網站或被入侵的網站（例如 ecpay.com 子網域、hsblood.org.cn、shopex.cn、amsdi.com.ph）→ 標記待人工確認，不作為典型正例。
- 同一批詐騙大量變體：newebpay*、dvrt*.ink、colaresearchclub.*、shopee*.github.io → 評估時依網域分組，避免同批網址同時落在訓練集與測試集。
- 大量 fbclid／utm 等廣告追蹤參數 → 正規化時去除，避免模型走捷徑。

## 4. 偵測邏輯

```
輸入網址 → 正規化 → 黑名單 →（未命中）白名單／品牌官方網域 →（未命中）ML 模型 → 風險判定與原因 → 存檔
```

- 黑名單比對分兩種層級：一般網域比對註冊網域；平台型網域比對完整主機名。
- 命中黑名單時直接判為高風險，並顯示通報日期與冒用對象。
- ML 輸出機率，依兩個門檻分成低、中、高風險。
- 品牌規則：主機名疑似冒用品牌（非官方、非同集團）者至少中風險（`app/services/risk.py`，2026-11-03 決定）。
- 判斷原因列出 2–3 項，例如「疑似冒用：藍新金流」「使用 .top 等常見詐騙網域結尾」。
- 結果用語為「未發現明顯風險跡象」，不說「安全」；附 165 反詐騙諮詢管道。
- 網址一律以去連結格式顯示。

## 5. ML

### 5.1 特徵（只用網址字串）

- 取自 Kaggle 特徵中可由字串計算的部分：網址與主機名長度、各類符號數量（. - @ ? & = _ ~ % / 等）、數字比例、子網域層數、IP 網址、punycode、連接埠、TLD 出現在路徑或子網域、可疑關鍵字（login、verify 等）、短網址服務、隨機字串程度（熵）、最長／最短詞長等。
- 台灣情境特徵：
  - 與 `brands.yaml` 官方網域的最小編輯距離（先做同形字正規化，例如 0→o、1→l、rn→m）
  - 品牌名加數字（newebpay11）
  - 可疑 TLD（.top .shop .cyou .icu .sbs .bond .xyz .online .store .life .my .cc .vip .buzz .cfd .ink 等，列在 rules.yaml）
  - 免費架站平台
  - 是否含 tw 片段

### 5.2 模型比較

| 候選 | 角色 |
|---|---|
| Logistic Regression | 基準，最容易解釋 |
| Random Forest | 常見樹狀模型 |
| LightGBM | 通常表現最好，較難解釋 |

### 5.3 評估

- 測試集分開報告：
  - A：Kaggle 測試集
  - B：政府資料最近數月（依時間切分＋依網域分組）
  - C：台灣正常網域（誤判率）；其中「含品牌字的正常網域」（brand_lookalike，如 teams.com.tw）單獨報告，
    14 個一半訓練、一半測試（`tw_legit_domains.csv` 的 split 欄，2026-11-01 決定）
  - D：仿冒變體
- 指標：PR-AUC、召回率、誤判率、預測耗時。不只看準確率。
- 門檻在驗證集上決定（中風險：抓到率 ≥ 90%；高風險：精確率 ≥ 95%），再用 A–D 報告成績。用測試集定門檻會使成績偏高（2026-11-01 修正，詳見 docs/dataset-plan.md）。
- 版本管理：資料雜湊、特徵版本、隨機種子、指標、門檻寫入 ModelVersion。

## 6. 系統架構

- Flask + SQLAlchemy 2 + Alembic + pyodbc（ODBC Driver 18）+ 本機 SQL Server 2022。
- MVC：controllers（Blueprint）、models（SQLAlchemy）、views（Jinja2）；ML、正規化、比對等放在 services 層。
- 角色：訪客（偵測網址）、管理者（匯入 XML、檢視統計、切換模型版本）。管理者頁面只允許本機存取。

## 8. 安全、紀錄與測試

- 安全：
  - 不連線被檢查的網址；網址以去連結格式顯示
  - CSRF 防護、偵測頻率限制、關閉 debug 模式
  - 資料庫使用專用帳號，只開放必要權限；密碼放在 `.env`
  - 複審加入上傳檔案的大小與內容檢查
- 紀錄：JSON 格式，同一次操作共用 request_id，記錄各階段耗時；網址只記錄主機名與雜湊，不記錄完整查詢參數。
- 測試優先順序：
  1. 正規化（含追蹤參數不變性）
  2. 黑名單的兩種比對層級
  3. 品牌近似判斷
  4. 風險門檻邊界值
  5. Playwright 測試整套流程、重複送出與異常輸入

## 9. 複審：165 話術規則（初審後實作）

165 提供的常見話術範本，可拆成四類線索：

- 冒用對象：銀行、快遞、財政部、購物平台、社群網站、金融機構、電信、醫療機構、「系統」
- 威脅或誘因：凍結、配送失敗或退回、未領退稅、付款異常或訂單暫停、異常登入或停用、系統升級、貸款核准、欠款或暫停服務、檢測報告
- 要求動作：點擊連結、身分驗證、輸入帳戶資料、確認地址或付款、繳費
- 有連結：OCR 擷取到網址

整合規則：
- 最終風險以網址為主；話術線索最多提高一級，並加入說明，不會降低網址風險。
- 簡訊自稱的品牌與網址不符（例如自稱蝦皮，網址卻不是蝦皮官方網域）時，列為判斷原因。
- 測試集：9 則範本各改寫 2–3 個變體，搭配已停止解析的網址做成簡訊截圖；另做一些不該誤判的正常簡訊。
- 簡訊原文不存檔，只保存命中的線索類別。
- 報告第 33 頁需列出 165 來源。
